Convenciones

Persona humana (PH) Persona jurídica (PJ) Compartido Ruta feliz Error / rechazo
  • PH: monotributista, responsable inscripto. Documentación llega automática vía 4i.
  • PJ: SA, SRL, SH, sucesión. Documentación se sube y revisa manualmente.
  • Detección: isPersonaHumana(entityType) en frontend/src/config/documentRequirements.js.
  • API base: /api/v1. Auth: JWT en header Authorization: Bearer <token>.

0Paso 0 — Solicitudes de alta

Pantalla

Tabla de solicitudes con búsqueda. Por fila: CUIT · Nombre · Tipo · Fecha solicitud alta · [Continuar carga de datos].

  • Sin estado de docs (la docu llega automática)
  • Filtros: tipo (mono / RI), rango de fechas
  • Orden por defecto: fecha desc

Eventos

  • onMount → GET /clientes?status=pendiente&tipo=ph
  • onSearch → debounce 300ms, query string
  • onClick(continuar) → router push /clients/onboarding/:id + POST /alta/:id/iniciar

1Paso 1 — Datos de entidad (autocomplete vía 4i)

Carga de datos

El backend recibe el id, llama a 4i y precarga:

  • DNI frente: nombre, apellido, dni, fechaNacimiento, sexo
  • DNI dorso: fechaEmision, domicilio
  • Persona única auto-vinculada (titular)
  • Facultades de firma: individual + general (default monotributista)
  • PEP: tick sí/no que llega desde el front de Mari (PSP client-facing). NO se carga acá ni se sube como documento.

Validaciones

  • CUIT válido (algoritmo módulo 11)
  • DNI 7-8 dígitos numéricos
  • Email formato + único en sistema
  • Flag PEP debe venir definido (true/false) desde Mari
  • Si OCR falla → permitir edición manual

2Paso 2 — Riesgo y perfil transaccional

Particular de PH: incluye campo NSE (nivel socioeconómico, 1 a 5).

{
  nosisResultado: 'sin_antecedentes' | 'con_antecedentes',
  nosisArchivo: File,
  nseNivel: 1 | 2 | 3 | 4 | 5,
  nseNotas: string,
  esPep: boolean,
  residencia: 'AR' | string,
  nacionalidad: string,
  actividad: string,
  antiguedad: number,
  materialidad: 'baja' | 'media' | 'alta',
  riesgoPuntaje: number  // 0-100, calc automático
}

3Paso 3 — Alta final

Resumen consolidado, edición inline de cualquier sección. Al confirmar:

  • POST /clientes con todo el payload acumulado
  • Si todos los docs están OK → status=aprobado
  • Si falta algo → status=pendiente + queda en bandeja

Estados (state machine)

solicitud_creada → en_carga → revision_riesgo → aprobado
                              ↘ pendiente (docs incompletos)
                              ↘ escalado_compliance (riesgo alto)
                              ↘ rechazado (PEP/screening hit)

Componentes React usados

  • ClientOnboarding (wizard padre)
  • DocumentForm (form auto-generado desde documentRequirements.js)
  • PersonPepUploader (DDJJ PEP)
  • RiskAssessment (NSE + matriz)
  • SignerConfiguration (oculto en PH, default individual+general)
Side-effect importante: el primer GET a /personas/:cuit/4i dispara una llamada billable a 4i. Cachear respuesta por 24h en backend.

Pantalla

1Paso 1 — Datos de entidad (manual, dos tabs)

Tab Docs

TipoDocumentos requeridos
SAEstatuto · Acta autoridades · Reg. accionistas · Poder admin · Balance
SRLContrato social · Acta asamblea · Reg. socios · Poder (opc) · Balance
SHContrato privado · DNI socios · DDJJ representante · Balance
SucesiónDeclaratoria herederos · Designación administrador · Solicitud AGJ · Ficha sucesión · DNI herederos

Por cada doc: split-view con preview PDF a la izquierda y formulario de campos extraídos a la derecha. Botones: aprobar · rechazar · observar.

Tab Personas

Cards con persona y secciones expandibles:

  • Datos básicos · Domicilio
  • Roles según tipo de entidad (mostrados dinámicamente):
    • SA: esPresidente · esDirector · esGerente · esAccionista · esApoderado
    • SRL: esGerente · esSocioSRL · esApoderado
    • SH: esSocioSH · esApoderado
    • Sucesión: esHeredero · esAdministrador
  • Facultades de firma: individual / múltiple / conjunta (con mínimo de firmantes)
  • Condición PEP: manual, persona por persona. Por cada persona vinculada el operador carga:
    • esPep: boolean
    • Si esPep = true: cargoPep, organismo, fechaDesde, fechaHasta, vinculoPep (ascendente, descendente, cónyuge, etc.)
    • Adjuntar declaración firmada (PDF) cuando aplique
  • Screening en listas (OFAC · ONU · GAFI · UIF) por persona — independiente del tick PEP
Diferencia con PH: en PH el PEP es un tick sí/no que viaja desde el front de Mari. En PJ no hay un único tick — cada persona vinculada (presidente, accionistas, gerentes, apoderados, herederos…) tiene su propia condición PEP que se carga manualmente, una a una.

Reglas de negocio críticas

  • Solo puede haber un presidente por SA.
  • Apoderado: por defecto individual + general (editable).
  • Firma conjunta: requiere minFirmantes ≥ 2 y se propaga a participantes seleccionados.
  • Beneficiario final: obligatorio identificarlo en SA/SRL.
  • En sucesión: o admin único O firma conjunta de herederos.

Side-effects compartidos

4i (solo PH)

OCR de DNI + DDJJ PEP. Llamada billable, cachear 24h.

Trigger: GET /personas/:cuit/4i

NOSIS

Búsqueda de antecedentes financieros. Genera PDF que se adjunta al expediente.

Trigger: POST /nosis/:cuit

Screening

OFAC · ONU · GAFI · UIF Argentina. Marca repetNotas si hay coincidencia.

Trigger: POST /screening/:id_persona

Autosave del wizard

  • Cada cambio dispara PUT /alta/:id/guardar con debounce 1.5s.
  • Backend persiste el borrador en alta_estado.data_json.
  • Si el usuario refresca, el wizard rehidrata desde el último guardado.

Checklist QA antes de release

  • Autosave funciona refrescando el browser en cada paso
  • Validación de CUIT con casos límite (CUITs falsos, dígito verificador erróneo)
  • Hit en screening bloquea avance y muestra escalado
  • OCR de 4i con DNI escaneado en mal estado → permite edición manual
  • SA con 2 presidentes → error
  • Firma conjunta con minFirmantes > participantes → error
  • Sucesión sin administrador ni herederos → error
  • Rol screen reader (a11y): tabs y stepper navegables por teclado
  • Carga concurrente de docs (10MB cada uno) sin timeout
  • Permiso operador no permite click en "dar de alta"
